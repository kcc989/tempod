# S16: Can every protocol schema become Rust types?

**Question (07, Spikes).** Do `Schema.toJsonSchemaDocument` plus `JsonSchema.toDocumentDraft07` plus `typify` produce types for every schema in `packages/protocol`, and does every fixture round-trip? Which types need a hand-written Rust version?

**Answer: yes, with two hand-written types (`Item`, `Empty`) and a small, tested normalization pass in `crates/protocol-gen`.** Run on Linux x86_64 with Rust 1.97.0. Nothing here needs a Mac.

## What was built

| Piece                       | Where                                                                      | Does                                                                                                                                                                                                                                                                                |
| --------------------------- | -------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Wire type registry          | `packages/protocol/scripts/wire.ts`                                        | Names every wire type the Mac app sees: shared types, item contents, workspace, hub and terminal channel messages, `ErrorBody`, `ApiMeta`, and the input and output of every function in `api.ts`. tempod's protocol is left out.                                                   |
| `bun run protocol:gen`      | `scripts/gen-schema.ts`, `crates/protocol-gen`                             | Writes `packages/protocol/schema/<Type>.json` (Draft-07, one file per type, other types referenced as `{"$ref": "<Other>.json"}`) and `Api.json` (the function table), then runs `protocol-gen`, which writes `crates/tempo-protocol/src/generated.rs` and formats it with rustfmt. |
| `bun run protocol:fixtures` | `scripts/gen-fixtures.ts`, `world.ts`, `samples.ts`, `channel-sessions.ts` | Writes `fixtures/types/<Type>.jsonl` (valid samples, one per line) and `fixtures/channel/<session>.jsonl` plus `<session>.expected.json` (end state and events of the web stores).                                                                                                  |
| CI check                    | `bun run --cwd packages/protocol protocol:check`                           | Runs both generators and fails if any output file changed.                                                                                                                                                                                                                          |
| Tests                       | `packages/protocol/test/fixtures.test.ts`, `crates/tempo-protocol/tests/`  | Effect decodes every fixture (excess properties are errors); Rust decodes and round-trips every fixture and every channel message, and decodes every expected end state.                                                                                                            |

Versions: `effect` 4.0.3, `typify` =0.8.0 (the newest stable release; 0.10.0-alpha.2 also exists), `schemars` =0.8.22, `prettyplease` =0.3.0, `syn` =3.0.8, `serde` =1.0.229, `serde_json` =1.0.154.

## Numbers

- 178 wire types: 29 enums, 143 objects, 5 unions (`Item`, `Instance`, `NewSource`, `WorkspaceServerMessage`, `HubServerMessage`), and `Empty`. 59 functions in `Api.json`.
- 238 Rust types in `generated.rs` (about 6,500 lines), plus `api::*` (one marker per function) and `wire::roundtrip` for the tests.
- 411 type samples and 6 channel sessions (94 messages, including two full 500-item backlog pages).
- `protocol:gen` takes 1.2 s warm (the first run compiles `protocol-gen`, about 20 s); `protocol:fixtures` takes 0.6 s. Running both twice gives no diff.

## Effect's output

The API in 07 works as written: `Schema.toJsonSchemaDocument(schema, { referencePolicy })` then `JsonSchema.toDocumentDraft07(doc)`. Shared types become references through `referencePolicy`, which receives the AST of the canonical JSON codec, so the registry keys each type by `schema.ast`, `Schema.toCodecJson(schema).ast` and its encoded side. The output describes the JSON codec (`Schema.toCodecJson`), not the plain schema. That shows in five ways:

1. `Schema.optional(X)` becomes `anyOf: [X, null]`, and `optional(NullOr(X))` becomes a nested `anyOf`. JSON null decodes to "absent" in the JSON codec only; the plain Effect schemas that the server uses reject `null` for an optional field.
2. `Schema.Number` becomes `anyOf: [number, "Infinity" | "-Infinity" | "NaN"]`. `JSON.stringify` never sends those strings.
3. `Schema.Struct({})` (`Empty`) becomes `{"not": {"type": "null"}}`.
4. Every object has `"additionalProperties": true`; every union is an `anyOf`.
5. `Schema.isPattern` checks are not emitted (ULID ids, `EnvName`, `HostPattern`, the `setClaudeToken` pattern), and string lengths are converted to code points (`isBetweenLength(20, 4096)` becomes `minLength: 10`).

## What protocol-gen changes before typify

Each rule is unit-tested in `crates/protocol-gen` and keeps the meaning of the wire:

| Rule                                                                                                       | Why                                                                                                                   |
| ---------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `"<T>.json"` refs become `#/definitions/<T>`; all files go to typify as one set of definitions             | typify does not follow file references                                                                                |
| Drop `"additionalProperties": true`                                                                        | It is the default; with it, typify does not build tagged enums (`NewSource` became an untagged enum of `Variant0..2`) |
| Drop the non-finite-number strings from a union with `number`                                              | Otherwise every number is an untagged enum                                                                            |
| Flatten nested `anyOf`, remove duplicates, unwrap a single member, and let `{}` (unknown) absorb its union | Gives `Option<T>` and `serde_json::Value` instead of nested enums                                                     |
| `{"not": {"type": "null"}}` becomes an empty object                                                        | typify 0.8.0 panics on `not` (`convert_not`)                                                                          |

## Hand-written Rust (`crates/tempo-protocol/src`)

| Type                              | Reason                                                                                                                                                                                                                                                                                                                                                                                  |
| --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Item`, `ItemContent` (`item.rs`) | typify can express the `anyOf` of ten item objects, but only as an enum whose ten struct variants each repeat the seven shared fields (`Variant0..9` before the normalization). The hand-written `Item` keeps the shared fields on the struct and `kind` with `content` as an adjacently tagged enum, flattened. Same JSON; `item.rev`, `item.content.text_mut()` work without a match. |
| `Empty` (`lib.rs`)                | Effect emits `not: null`, which typify cannot convert. `struct Empty {}` serializes to `{}` and accepts any object.                                                                                                                                                                                                                                                                     |

typify is told to use them with `with_replacement`, so `WsItems.items` is `Vec<crate::Item>`. Not schemas, also hand-written: the `Function` trait and `Method`, `PROTOCOL_VERSION`, and the close codes of 02.

## What the generated Rust looks like

- Every `Schema.Number` is `f64` (timestamps, `rev`, counts); `Schema.Int` with safe-integer bounds is `i64`. JSON `5` and `5.0` are the same value.
- Object fields are `snake_case` with `#[serde(rename)]`. Optional fields are `Option<T>`, skipped when `None`; required nullable fields (`turnId`) are `Option<T>` that must be present. Records are `BTreeMap`.
- The channel unions are `#[serde(untagged)]` enums of the message structs; each struct has a single-value `type_` enum, so exactly one variant matches. Variant names: `WorkspaceServerMessage::Hello(WsHello)` … `Pong(WsPong)`; `HubServerMessage::HubHello(HubHello)`, `HubWorkspace`, `HubWorkspaceRemoved`, `WsPong` (no common prefix to strip, because of the shared `WsPong`).
- `NewSource` is `#[serde(tag = "kind")]` with struct variants; `Instance` and `ConfigOption.options` are untagged.
- Literal `1` (`v`, `protocol`) is a checked newtype (`WsHelloV(f64)`). Non-empty strings (`NonEmpty` in `api.ts`) are checked newtypes built with `parse()` or `try_from`.
- Unknown fields are ignored, so additive fields (05) decode. A new message type or enum value fails to decode, as it does in the web store; the client drops that message.

## Round-trip rule

Decode the fixture, encode it, decode again: the two values must be equal, and the encoded JSON must equal the fixture, where numbers compare by value and an optional `null` that was left out counts as equal. Every one of the 411 samples and 94 channel messages passes.

## Not done here

- The Rust stores in `crates/tempo-client` must replay `fixtures/channel/*.jsonl` and match `*.expected.json` (07, Testing, Stores). The fixtures exist; the store tests belong to that crate and to `apps/tempo`.
